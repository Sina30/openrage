# Clothing tool design

Where a GTA V clothing and ped-component tool lives for OpenRage (a project system, a plugin, or a derived app), weighed against Durty Cloth Tool, grzyClothTool and Vestium.

Status: proposal of 2026-10-07; the owner has not ruled on the questions below one by one, and gave go to [Workbench_Plan.md](Workbench_Plan.md), which takes this study's recommendations as defaults and orders the work. [R44f](Roadmap.md#r44f-payload-and-gpu-access) and [R46](Roadmap.md#r46-first-plugin-a-clothing-tool-on-openrage) stand until a wave rewrites them, and an accepted answer moves to [Project_Context.md](Project_Context.md). Waves B and F of the plan built the typed ped metadata and the engine, wave H the screen over it ([what the Wardrobe workspace builds](Workbench_UX_Design.md#what-the-wardrobe-workspace-builds)), wave L the extension kinds, the cloth painter and the second kind of content ([what the extension builds](Project_Model_Design.md#what-the-extension-and-the-second-kind-of-content-build)), and [what the engine builds](#what-the-engine-builds) says where the build differs from the text below.

## Verdict

Build the pack-making tool as a **first-party "Wardrobe" module of an OpenRage project**, with its engine in a headless domain crate, and keep plugins for what a community adds to it. Do not build it as a plugin, and do not start a separate app.

- **The project system is the right home, built in the right order.** One concrete module type first (clothing), the generic substrate extracted when a second type (addon peds) needs it; [Project_Model_Design.md](Project_Model_Design.md) says how modules, outputs and links make up a project. A generic framework first would freeze a project format before any second consumer has shaped it, and [R48](Roadmap.md#r48-projects) already warns that project formats are forever.
- **A plugin cannot carry it today, and making it able to costs more than the tool.** The plugin surface has six widgets, no image, no table, points and lines in the viewport, no read of a sibling file, no disk write, no job and a synchronous three-second ceiling. A pack builder needs every one of those. Extending the host until it fits moves the tool into the host and leaves a thin shell in WASM.
- **A derived app buys freedom OpenRage does not need and loses what it has.** Every crate is `publish = false`, the repository is private and the publication questions are parked (R66h); the dressed-ped preview, undo, jobs and project code live in `src/`, not in a library.
- **The roadmap names two tools with one name.** R46 describes per-vertex cloth physics authoring, which fits the plugin surface and stays a plugin. "A DurtyClothTool equivalent" is a pack builder, and no row owns that.
- **The edge over the three incumbents** is not more checkboxes. It is what only an owned-value reader and writer gives: a deterministic canonical output, a verified reload of everything written, lossless repair on request, both targets in one process, a headless build for CI, and a build diff that protects a server's saved outfits from a renumbering.

Choosing this amends the owner's direction of 2026-10-05 recorded in R44f ("the clothing tool is a WASM plugin"), so it needs a ruling ([decisions](#decisions-asked-of-the-owner)).

## What the question contains

A clothing tool is three layers, and the three options differ in where each lives.

| Layer | What it is | Why it matters |
|---|---|---|
| Model and engine | The pack (collections, slots, garments, variations, flags), the name resolver, the slot allocator, the validators, the build planner, the executors, the verifier | Pure logic over `or-io`. It is where the bugs that crash a game server live, so it must be testable without a window |
| Surface | A slot list, a garment inspector, a dressed-ped viewport, a problems list, a build dialog, bulk edits | A four-hour daily workspace, not a dialog |
| Extension | Validators, config emitters for server frameworks, import resolvers, texture filters, panels | Fast-moving, community-specific, and the reason a plugin system exists |

The incumbents are all one block of the first two layers with a little of the third. OpenRage can separate them, which is what makes the third layer cheap.

⚠ The roadmap's R46 and the owner's record both say "a DurtyClothTool equivalent" and then describe cloth physics. Durty Cloth Tool's changelog shows cloth physics (a `.yld` attach, and wind in version 4) as one feature among dozens; its identity is the pack builder. R46's own text ends with "the surface may prove insufficient, which is the point", and this study finds that it is insufficient for the builder and sufficient for the physics.

## What users hit

Ranked by how often issues, forum threads and comments return to them, with the 2026-10-07 reading of the three trackers.

1. **Stability and data loss.** Startup crashes, a rebuild that deleted a user's resource folder, no atomic autosave. OpenRage's rule of writing to a fresh folder and swapping, plus the verified reload, answers it by construction.
2. **Singleplayer at scale.** A very large pack corrupts an archive near the 65,535-entry limit; hats and props break; `setup2.xml` has a hard-coded order. OpenRage has an archive writer with nested archives and defragmentation, and a DLC writer, so this is a place to be better, not just equal.
3. **Hair and hat behaviour.** The hide-hair and hair-scale features misbehave in grzyClothTool, and Vestium lists the meaning of one expression value as unresolved. Both come from metadata the tools write without being able to read back what the game does.
4. **Weak duplicate and warning workflows.** A metadata hash gives false positives; users ask to toggle missing-LOD warnings and to downsize in bulk by a ratio.
5. **Replace packs, other peds, non-clothing items.** Asked of grzyClothTool, answered by Durty only behind a paywall.
6. **Paywall and trust.** The single largest reason grzyClothTool exists.
7. **Onboarding.** No wiki; tutorials are community videos.
8. **No way into CI.** Every server team builds by hand.
9. **Renumbering breaks live servers.** Moving or deleting a garment shifts the ids that saved outfits, shop tables and sold packages point at. Vestium keeps Durty-compatible shop hashes for this reason; nobody diffs two builds.

## The options

Four ways to build it, then a score.

### Option 1: a project system first, clothing as one module type among many

The owner's first idea: a generic project concept for clothing, maps, peds, props and weapons.

- **For.** The substrate is real and shared: a manifest, a content-addressed asset store, originals, history, rules, a plan then an executor, jobs, targets. One interface for every kind of pack. It is where the roadmap already points (R48).
- **Against.** A generic framework drawn before a second module type exists is a guess, and the schema is forever. Vestium's project model is clothing-shaped and works because of it. The module types differ more than they look: a map's unit is an entity and a placement, a clothing item's is a slot and a variation, a weapon's is a component and an attachment point.
- **Long term.** Strong if it is extracted, weak if it is designed up front.

### Option 2: a WASM plugin that opens a popup

The community installs it from the plugin manager.

- **For.** It matches the owner's direction of 2026-10-05 and the sandbox model: untrusted by default, capability-controlled. Distribution is a file. A plugin cannot damage the editor. It is the right shape for cloth physics.
- **Against, measured.** A guest gets the active document's bytes and nothing else: no sibling texture, no other open document, no install read, no write to disk, no project data, no job, no thread. The interface has six widgets (no image, table, tree, combo, tabs or drag and drop). The viewport takes points and lines, one pixel wide. A call is synchronous on the editor's thread, so the 4 billion instruction budget is the longest freeze; parsing the largest `.ydd` inside a guest costs more than that, and a pack is hundreds of files. A modal popup is the wrong container for a long session. `openrage-cli` does not embed the host, so there is no headless build.
- **To make it fit** the host would need a read of the install, a read of sibling documents, host-drawn meshes from guest descriptions, an image widget, host-run jobs, plugin-owned project data and gated output writes: a large piece of work that also contradicts the stated line that a guest cannot touch the GPU unless the host draws for it. The tool's real logic would move into the host.
- **Long term.** Good for extensions, wrong for the core. The ABI has a version number and an older plugin still loads, so changing it costs a new version and not every plugin's rebuild, but it should be changed for what extension needs, not for a tool.

### Option 3: a derived app on `or-io`

A separate product that links the libraries (or speaks to `openrage-cli serve` as a subprocess).

- **For.** Its own identity, onboarding and release cadence; the clothing audience gets a tool, not an asset editor; no constraint from the shell's budgets. The incumbents are standalone, and Vestium is the owner's proof that a clean product ships this way.
- **Against.** `or-io` is not published: every crate is `publish = false`, the repository is private and R66h is parked, so a derived app depends on a git revision and credentials. The licence provenance travels with it (permissions without a written grant, a bundled key snapshot, engine names). The preview, undo, jobs and project code are in `src/` and would be rebuilt or extracted first. Two apps mean two update channels and a split user base. A 0.x API changes under it. The subprocess route cannot draw in the editor. The linked media crate is AGPL, which makes a combined binary AGPL.
- **Long term.** A fork's maintenance cost for a solo maintainer, and the product that matters most (the editor) would fall behind its own library.

### Option 4: a first-party module inside OpenRage, with a headless engine and plugin extension

Option 1 built in the right order, with Option 2 where it fits and Option 3 as a packaging step if wanted.

- The engine is a domain crate with no UI. The app has a Wardrobe workspace. The CLI has pack verbs. The plan is data, so a plugin or a script reads the plan and adds files.
- It reuses the viewport, undo, jobs, project and consent that exist, and it keeps the layer rule (foundation, io, title, domain, runtime, app).
- **Against.** It amends R44f and so needs a ruling. It adds weight to a shell that has a per-file code budget and a deliberately flat state, which the design answers by keeping logic in the crate and the panels thin. It makes the owner the maintainer of a large first-party feature.
- **Long term.** The best: the headless engine is what survives any later change of surface, including a standalone flavour.

## Recommendation: Wardrobe

The working name is Wardrobe; the owner names it.

### Principles

1. **The plan is data.** A pure function turns the model into an explicit build plan (files, metadata documents, limits); a thin executor writes it. Everything testable is before the executor. This is Vestium's best idea.
2. **Write, reload, check.** Every produced file is opened again with `or-io` and held to the plan's invariants before the build reports success. The canonical form makes two builds of the same project byte-identical, which makes a diff meaningful.
3. **Nothing leaves the project folder except a build, and a build goes to a fresh folder that is swapped in.** Originals are kept; history is more than undo; an autosave never overwrites the manifest.
4. **Positions are stable, and the build says what moved.** A lockfile pins slot ids; a renumbering is a reported event with a migration map.
5. **Rules are data.** Typed codes, severities, waivers with a reason, per-project overrides, exportable.
6. **The engine is headless and the surface is thin.** The same crate serves the app, the CLI and CI.
7. **A plugin extends and never hosts.** Plugins get data in and data out.
8. **No claim the game has not confirmed.** "Verified in game" is a recorded state per target, set only by a tester ([risks](#risks)).
9. **A field of a game structure is named only as the engine names it.** The names of the metadata a pack states and of every field a typed structure declares come from the engine, through the corpus, the testimony and the local layout references, as [OR_IO_Specification.md](OR_IO_Specification.md) records in D15, and never from a guess, from a tool's own spelling or from what a value seems to do. A table decoded from the executable gives a hash, a type and an offset and no name, so a field is named from it only where a name the engine states resolves the hash; a field whose name is not proven is reported as unproven, and a screen says the field is not named rather than call it something.

### Architecture

| Layer | Where | Notes |
|---|---|---|
| Typed ped metadata | or-io metadata | `meta::typed` declares by hand the ped variation family, matched against each document's own type table, with a writer that grows an array and refuses an index the file does not hold |
| Model, resolver, allocator, validators, planner, executors, verifier, differ | a new crate in the domain layer (working name or-wardrobe) | Depends on or-io, or-title, or-interchange; never on a renderer or on egui; the media crate stays out |
| Dressed-ped scene | runtime and app | The crate states which drawables and textures a slot selects; the scene draws them |
| Workspace, panels, commands, module registration | app | A registered module type, panels in the registry; the shell's file budgets hold |
| Pack verbs | CLI | validate, build, diff, import, and a plan emitter |
| Extension | plugin host and subprocess | Validators and emitters as data-in, data-out kinds; scripts read the emitted plan |

#### The project system

A project has no type. It holds typed modules and declares its outputs, and [Project_Model_Design.md](Project_Model_Design.md) owns that model.

- **Build generically from the first day what is free to generalise:** the content-addressed store with originals, the rule registry, the plan-then-executor split, jobs, targets.
- **Keep module-specific:** the slot model, the metadata builders, the rules and the preview scene.
- **Extract the substrate when the second module type arrives.** The natural second one is the addon ped, which shares the ped metadata family.

| Module type | Its unit | Output | Shares with clothing |
|---|---|---|---|
| Clothing | slot and variation | FiveM resource, singleplayer DLC, `.oiv` | n/a |
| Addon ped | a model with its component set and clip sets | the same targets plus ped definitions | ped metadata, textures, slot model |
| Props and maps | placement and archetype | resource or DLC with map data | assets, rules, plan, targets; the editor itself stays a plugin (R47) |
| Weapons | component and attachment point | weapon metadata plus models | assets, rules, plan, targets |
| Vehicles | model with handling and variation data | vehicle metadata plus models | assets, rules, plan, targets |

The flow from nothing to a pack:

1. Drop a folder. An import report lists what was resolved and what needs a decision, in one dialog with "apply to selected".
2. Problems appear live as files load, each with a fix or a waiver.
3. "Fix all safe" runs a pipeline (repair, LODs, textures, order) and reports each step; one history step per action.
4. The dressed ped shows the result with the real base outfit, heel floor, hat hair squash and palette tint.
5. Build shows a plan first (files, limits, what moved since the last build), then writes, reloads, checks and reports.
6. The project is a folder a team can put in Git, and the same build runs headless in CI.

### The power features of wave P37

Wave P37 built the rows of the power-user catalogue that the second plan took (ruling R18), in `or-wardrobe` and over it:

- **A query line.** `query` reads `tag:wool slot:jbib polys>5000 lod:missing` into terms ANDed together, each turned round by a `-`, and the words that name no term as names searched for with their letters in order (a word with a `-` in front leaves out the garments it finds). The polygon count is the triangles at the high level of detail of the garment's model, summed over its drawables, from the same `Measure` the rules read for a compiled model and, for a model that is a drawables source, from the JSON header of the glb of each drawable (each mesh is at the level the cook gives it: its node's `extras.rage.lod`, else the level its name states, else the first, so a glb that a modelling tool exported again still counts), which counts without a cook; `lod:missing` is the case the rule `lod-missing` names, whatever the pack set that rule to; `is:duplicate` and `duplicate-of:<name>` use the pairs the rule `duplicate-content` finds (`rules::duplicate_pairs`). A saved query is `{ name, query }` in `wardrobe.json`, the text of the line, so it diffs well and follows the pack through Undo, the versions and a package.
- **A bulk edit.** `bulk::dry_run` applies an `Edit` to a copy of the pack, garment by garment, and says for each what differs (`changes` words a difference as the field's name, what it was and what it is), which garments refuse and how many are left as they are; `bulk::make` is `edit::apply_all` in one `revise`, so one Undo takes all of it back.
- **Review.** `review::between` compares two packs by the garment's stable id and each texture by its place among the garment's textures; the versions are those `backup` keeps, and a side that is none is the pack as it is. The app draws the garments that differ as each version held them with the Pictures tool.
- **Credits.** `credit` (`author`, `url`, `licence`) in `asset.json` is what a source says of who made it; `credits` reads it from every source the pack names and the option `credits` of a build writes `credits.md`.
- **A pack package.** `pack_package` writes the pack as a zip, the header `openrage-pack.json` first and the files in path order with a fixed time, so a pack of sources that did not change is a file that did not change; an import refuses a name that leaves its folder, a compiled game file outside a source and a package that is not one, and leaves nothing behind.
- **Tag rules and sizes.** The build option `include_tags` keeps a garment its place and drops its files when it carries none of the words (`Garment::hold_its_place`); `sizes` ranks the files of a plan by garment and by slot from the owner of each (`Planned::owners`), `or_project::sizes` by content from the content that wrote each (`Plan::made_by`), and `sizes::dependencies` lists what the garments name.

What is not built: the memory-budget solver, a 3D comparison between two revisions beyond the pictures of the two sides, and **a file for each garment**. `wardrobe.json` is one file for the whole pack, so two people who edit different garments of one pack change one file and Git can only merge them as text; a folder of `<id>.garment.json` files and a small index would let it merge garment by garment. It is recorded here and not built, because every reader and writer of the pack would change and the saved queries, the versions and the lock would have to follow.

### What it will not build

alt:V and RageMP output (Durty marks both deprecated and ends RageMP support), a Blender dependency, an account or licence system, a promotional launch popup, tattoo and overlay editing in the first release, and an in-app texture painter (the live external editor round trip covers it).

### What the engine builds

Wave F of [Workbench_Plan.md](Workbench_Plan.md) built the headless engine, in `crates/domain/or-wardrobe`, with the typed metadata under it in `or-io` and `openrage-cli wardrobe` over it. A project holds a clothing pack as one clothing content (`type` `clothing`, with a `path` to its folder), and the folder holds `wardrobe.json`. What the build agrees with in the sections above, and where it differs:

- **The model.** A pack has a name, the collection of each ped (`mp_m_<pack>` and `mp_f_<pack>` unless it says otherwise), garments and waivers. A garment has a stable id, a ped, a slot, a position if somebody pinned one, a skin, a model, alternates, variations, the metadata the engine states under its own names (`propMask`, `pedXml_audioID`, `renderFlags` and the rest) and the expressions it adds to the creature metadata. A garment with no model holds a place, as the gaps of the staged packs do. An id is one plain file name, and a `wardrobe.json` edited by hand whose garment has any other is refused when it is read (`a_file_whose_garment_has_an_id_that_is_no_plain_file_name_is_not_read`). Only the two freemode peds are dressed; the addon ped is the second kind of content, not this one. A texture can hold the shop entry an import read for it (`shop`) and an id somebody chose (`shop_id`), and the pack's `shop` holds the entries that point at no garment (`unplaced`) and the files a manifest registers with the shop that the engine does not read (`carried`). `wardrobe.json` is schema 4: a garment has cloth when `cloth` links a file, no metadata key says so, and a schema 1 file is read with its `ownsCloth` moved to what replaced it and saved as the current schema (`a_file_of_schema_1_is_read_with_its_cloth_moved_to_what_replaced_ownscloth_and_is_saved_as_the_current_schema`). The keys `alternates` and `firstPersonAlternate` were first written under schema 2, so an OpenRage that reads schema 2 reads them and drops them, and the saved queries (`queries`, wave P37) are first written under schema 4 for the same reason, so that an OpenRage that reads schema 3 does not drop them on its next save; a file is written as the current schema so that one refuses it with a sentence that names both numbers (`a_file_of_a_schema_this_build_does_not_know_is_refused_with_a_sentence_that_says_which`, `what_a_file_writes_is_schema_4_because_a_reader_of_3_would_read_it_and_drop_its_saved_queries`), and a schema 2 or 3 file is still read whole and saved as the current schema (`a_file_of_schema_2_is_read_as_it_was_written_and_is_saved_as_the_current_schema`, `a_file_of_schema_3_is_read_whole_and_is_saved_as_schema_4`). A prop's slot is the engine's file word, so the hip prop (anchor 8) is `p_lhip` (`the_hip_prop_is_spelled_as_the_engine_spells_it`); no file name or content of the staged corpus or of the server's reference pack carries either word (a search of each for `p_lhip` and `p_hip`; the staged corpus's only hits are the ped names ending `Ramp_Hipster`, and the reference pack has none), so the word is the one the engine's table of prop slot names states, and `p_hip`, which an earlier OpenRage wrote, is still read from a file name or a `wardrobe.json` and saved as `p_lhip` (`a_file_named_with_either_word_is_the_hip_prop_on_import`, `a_wardrobe_json_that_says_p_hip_is_read_and_says_p_lhip_when_it_is_saved`).
- **Names.** The resolver reads the ped, slot, position, skin, variation letter and tint out of a file name, and marks what it cannot read; the layout is the one the staged resource has (`stream/<pack>/<ped>_<collection>/<slot>/<ped>_<collection>^<slot>_<number>_<skin>.ydd`, `_p_` for the props, the metadata beside them and the creature metadata in `creaturemetadata/`). `numAlternatives` counts the alternates of a drawable, `<model>_1.ydd` and on: the 9 male drawables of the staged resource that state 1 are the 9 male models that have a `_1` file.
- **Positions.** A pinned garment keeps its place whatever happens around it; one with no pin takes the lowest place no pin holds, in the order of the list, up to 255 a slot. So removing a garment before unpinned ones renumbers them, and the build says so by stable id, with a redirect map from the name the game saw to the name it will, which `openrage-cli wardrobe diff --redirects` writes. An import pins every garment at the number its name carries, since that number is what a server's saved outfits already hold.
- **What an import leaves out.** It lists, with the reason, every file it cannot place: a model, texture or cloth whose name does not state its place, a cloth with no model at its place, a prop's cloth, a second cloth for one place or one that names the other skin than its model, a cloth beside a model whose metadata does not state `ownsCloth` (the game does not use it, so it is not linked and stays a loose file), a `.yft` (a freemode component has no fragment), a prop stated at one of the four anchors the engine's table names past the hip and no staged document states (`ANCHOR_LEFT_FOOT`, `ANCHOR_RIGHT_FOOT`, `ANCHOR_PH_L_HAND` and `ANCHOR_PH_R_HAND`, anchors 9 to 12), which is named with its anchor and is no slot of a pack (`a_prop_at_an_anchor_no_staged_document_states_is_left_out_by_name_and_not_dropped_silently`), and a `.ymt` that neither the variation nor the creature reader opens (`a_file_of_a_pack_that_nothing_here_builds_is_left_out_with_the_reason_and_not_dropped`). A file of another kind, such as the manifest or a data file, is not a file of a pack and is not listed.
- **What was measured and holds** (over the staged metadata corpus and the server's resource, at `4557857b`). In every texture of a drawable `texId` is 0 for `u` and 1 for `r`; a drawable has one component info (in each of the compared documents below), and the packs do not agree on the order they list them in, so a plan lists them by slot and position and the comparison reads them by those two numbers; the props are sorted by anchor and position, each anchor lists how many textures each of its props holds, and `availComp` names the data in order, in all 1,839 staged variation documents; `bHasTexVariations` and `bHasDrawblVariations` agree in all 1,839 and follow nothing the document holds. 1,772 of the 1,839 come back out of an import and a plan with the same drawables, textures, component infos, props and anchors; 64 are left out because their component data and slots do not pair one to one, and 3 because they are super LODs whose drawables wear no texture (`a_staged_variation_document_survives_being_held_as_places_and_planned_again`).
- **Against a resource that exists.** The plan of the server's clothing resource, 13,331 drawables and textures with 12 alternates among them, has exactly its files, the variation metadata of both peds in meaning and its creature metadata (`the_plan_of_a_reference_pack_matches_the_reference`, which takes the folder from `OPENRAGE_REFERENCE_PACK` and skips without it, the resource being in no repository). It was planned from an import of the folder in place, at `Depth::Stat`: nothing was read or written there.
- **Shop metadata against the same resource.** The `data/<ped>_<collection>.meta` of each ped has the header the plan writes (`pedName`, `dlcName`, `fullDlcName`, `eCharacter`, `creatureMetaData`), every entry has the elements the plan's have in their order, every value of an element that is no index is one the resource writes, and every entry of the resource is the plan's, counting an entry listed twice twice and leaving the `uniqueNameHash` out: an entry the resource lists for a texture it has no file for is kept as stated and written back, and so is every element an import kept, `forcedComponents` among them, in `the_plan_states_the_shop_metadata_the_reference_registers_its_collections_with`. The plan has more entries than the resource lists, which leaves some drawables out of its shop. The comparison found that the plan wrote the bare `eCharacter` of the male files for the female ped too; the female shop files state `SCR_CHAR_MULTIPLAYER_F` in all 21 that the server's resources hold, the male ones the bare form in 19 and `SCR_CHAR_MULTIPLAYER_M` in 2 (counted by hand, no test holds the count), and the plan now writes the bare form for a male and the `_F` form for a female. The ids (`uniqueNameHash`) are not compared in that suite: the plan writes the ones an import read, which the next item holds to the resource.
- **A shop's own metadata.** A server that left Durty Cloth Tool, or never used it, has shop files and entry ids of its own, so compatibility is not Durty's alone: `or_wardrobe::shop` reads them. It finds the files a resource's manifest registers as shop apparel data (a line `<directive> '<type>' '<path>'`, whichever directive ends in `data_file`) and any file offered whose root element is `ShopPedApparel`, and resolves each entry to the texture of a garment by its ped, its `eCompType` or `eAnchorPoint`, its `localDrawableIndex` or `localPropIndex` and its `textureIndex`. The `uniqueNameHash` is kept as the text the file wrote, because a name the game hashes or a run of 12 hexadecimal digits does not fit 32 bits; it becomes the default id of that texture with the entry's `cost` and its other elements, and a build writes it back unchanged. An entry that points at no garment is kept in the pack and written back, and a ped with no garment at all but such entries still gets its shop file, registered in the manifest, with no variation metadata (`entries_kept_for_a_ped_that_has_no_garment_are_still_written_registered_and_verified`); a texture no entry names gets the build's name (Durty's when `durty_hashes` asks), and two entries claiming one id, case aside, are findings a waiver can set aside (`shop-entry-unplaced`, `shop-id-clash`). Another file the manifest registers with the shop, such as a server's own `.spak`, is carried unchanged under the line that registered it. Against the server's resource (`a_server_pack_with_its_own_shop_metadata_is_imported_and_written_back`, which takes the folder from `OPENRAGE_REFERENCE_PACK`, skips without it and only reads it; measured at `a2920ff2`): its 2 shop files state 11,138 entries, 11,063 of which resolve to a texture and 75 point at no garment; 73 garments have a texture no entry names; 9 ids are claimed by more than one entry; 5,213 ids do not fit 32 bits; the plan writes all 11,138 back with their ids and 380 more, named by the build, for textures no entry names; and a second import of the output, made over empty stand-ins for the models and textures so that none of its 4 GB is copied, resolves 11,443 of 11,518 entries, every id the first import resolved unchanged. Its 2 `.spak` files are carried. It ships no cloth, so what the game does with a cloth shipped while the metadata does not state `ownsCloth` is not measured and no import links one.
- **Edits and Undo.** [`or_wardrobe::edit`](../../crates/domain/or-wardrobe/src/edit.rs) makes every change a screen makes, and [Wardrobe_Parity.md](Wardrobe_Parity.md) says which of the incumbents' rows the Wardrobe has. `revise` reads the pack, changes it, writes it and keeps the pack as it was and as the change left it, and `undo_revision` writes the first back and is refused when the pack is no longer the second, so a screen takes any edit back without a rule of its own for it; `locate_texture` and `remove_texture` are the fixes of a texture that is not there, and `moved` says which garments took another place when one left or changed. A drop never adds a garment the pack already holds, which is one of the same ped and slot with the same model bytes and, where the drop brings textures, the same texture bytes, and its report names them (`a_folder_dropped_twice_adds_its_garments_once_and_the_second_drop_says_how_many_it_left`, `undo_after_the_fix_of_a_duplicate_restores_the_garment_the_fix_removed`).
- **Operations on a garment.** Wave P20 adds the operations a creator does by hand, each a `Revision` that one Undo takes back whole. `or_wardrobe::replace` puts another file in the place of a model or a texture: the file is decompiled at the door into a source folder of the pack, which the garment names in place of the old one, so the name the garment ships under comes from the garment and every setting of it (place, pin, skin, tints, texture ids, flags, shop ids) stays, and an image makes the texture as a drop does; the file or source it replaced is not touched, so a garment that names it too keeps it, and a place held is given the file the same way (`a_replaced_model_is_a_source_the_garment_names_and_the_old_file_stays_where_it_was`, `a_model_another_garment_names_too_stays_with_that_garment`, `a_place_held_takes_the_model_it_is_given_and_undo_takes_the_source_out_again`). Undo names the old file again and takes the new source out, one step at a time (`a_second_replacement_leaves_the_first_and_undo_goes_back_one_step_at_a_time`); the file a replacement wrote over, which `or_wardrobe::rewrite` kept by hash, is the one thing the door no longer produces. `duplicate::to` copies garments to a ped with a copy of every file (a texture written over in place would change both garments), the flags and tints, no shop id, and the lowest free place of the slot (`a_jacket_is_copied_to_the_female_ped_with_its_files_and_flags_and_undo_takes_the_copy_out`); the copy ships the same model as the garment until its model is replaced, and no rule says so: the duplicate rule compares garments of one ped and slot, and a copy is made for the other ped. `edit::reorder` swaps the place of a garment with its neighbour's in its slot: free garments swap their order, and when either is pinned both are pinned at the places they swap to; the name the game sees changes for both and the next build's diff reports them by stable id (`two_garments_that_are_not_pinned_swap_their_places_and_stay_free`, `pinned_garments_swap_pins_so_each_is_where_it_was_asked_to_be`). `variations` adds a texture from a `.ytd`, takes one out, moves one to another letter (a letter is its place in the list, so moving renames the ones it passes) and tints one, each refusing a row that names a file the texture at that place no longer has (`moving_a_texture_renames_the_letters_it_passes_and_its_tint_and_flags_go_with_it`). `export` writes a garment's files, or one texture's, under the names a build gives them, which a drop reads again, and overwrites nothing (`the_files_of_a_garment_are_written_under_the_names_the_game_gives_them_and_a_drop_reads_them_again`). `edit::apply_all` makes an edit to a list, all or none, so one revision is one Undo for a removal, a ped or a slot of three garments (`three_garments_removed_together_come_back_together_with_one_undo`); the screen that picks a list is wave P21's.
- **Import breadth.** Wave P22 changes what `edit::add_clothes` takes. A file whose extension is one `or_io::authoring::texture_import` reads (PNG, JPEG, TGA, BMP, TIFF, DDS, PSD, HDR, EXR) is a texture by that extension and is named as a `.ytd` is; one named as a texture is authored as a textures source of its variation (`or_source::create::author_textures`), which holds the pictures and no DDS and is compiled once in a scratch folder before it is kept, so a refusal of the compile (floating-point light with no rule to bring it down, a size a texture cannot have) leaves the picture out with the compile's sentence and the garment keeps its other textures (`a_dropped_image_becomes_an_authored_textures_source_of_its_garment_in_every_format_and_undo_takes_it_out`). The source states no platform; a build compiles it for Legacy, Enhanced or both. A picture that is named as no texture is left out and not given to the only model. `resolve` reads a name behind a chain of prefixes from its last name (`dlc^` and the like) and an image as a texture, and a file that opens with `FXAP` is left out by name in a drop and in an import. A duplicate, in `rules` and in a drop alike, needs the same ped, slot, model bytes and texture bytes. `add_clothes_watched` takes a `Watch` (an `or_job::Progress` and an `or_job::Cancel`): it counts the files it reads and the garments it copies, looks at the flag as it goes, and a drop that is stopped removes what it copied and writes nothing; the ceiling of a folder is a million files (`a_drop_says_how_far_it_has_got_and_ends_at_the_whole`). Dialog and header are the screen's ([Workbench_UX_Design.md](Workbench_UX_Design.md), What a drop takes in); the app's `resolve_garments` applies a ped and a slot to a list in one `Revision`.
- **Tags, groups and search.** Wave P21 gives a garment two words of its own that a person writes and a build reads only through the inclusion rule of a build (wave P37, [the power features](#the-power-features-of-wave-p37)): `tags`, any number of them, and `group`, one name, both in `wardrobe.json` beside the label and only where somebody wrote them (they are not in `Meta`, which holds the engine's names). `edit::apply_all` makes `AddTag`, `RemoveTag` and `Group` to a list as it makes every edit, so a tag on three garments is one Undo; the same word in another case is the same tag and a tag of nothing is refused (`tags_and_a_group_are_set_over_a_list_all_or_none_and_a_pack_without_them_writes_none`), and a build of a pack is the build of the same pack without them (`a_build_is_the_same_with_tags_and_a_group_as_without`). `search::terms` is what a garment is found by, each word apart: its place, its slot, its name, the name a build gives its model (`search::game_name`, computed by the layout the build uses) and its group and tags; the list matches each word of a query, as letters in order, against one of them (`a_garment_is_found_by_its_place_slot_name_game_name_group_and_tags`).
- **Rules.** `RULES` lists them with a code, a severity and whether a waiver can set a finding aside: the pack and collection names, a garment with no ped or slot, two pins at one place, a full slot, a path that leaves the folder, a model or texture that is missing or that its reader refuses, a model with no texture, more than 26 textures, a metadata value that does not fit its field, expression arrays of different lengths, two garments of one place stating different expressions in the creature file, a duplicate model found by content, a slot of 256 textures or more whose count wraps, a garment missing its cloth (its metadata states `ownsCloth` and no cloth file is linked: `cloth-missing`, an error a waiver with a reason sets aside), a cloth that is linked and not a file, or that its reader refuses (`cloth-file-missing`, `cloth-unreadable`), a cloth linked where the game reads none (`cloth-ignored`, a warning), two shop entries written with one id and entries kept for want of a garment (`shop-id-clash`, `shop-entry-unplaced`, warnings a waiver sets aside), a place held, and a waiver that gives no reason or names no rule. A finding the pack has waived, with its reason, does not stop a build; an error no reason could mend cannot be waived. A fix that applies a rule's remedy is `edit::remedy`: it says in a sentence exactly what it changes and offers itself only where no choice is needed, for a position clash (the garment refused is unpinned), a pin past the last place, a duplicate (the later garment leaves the pack, its files stay), a garment missing its cloth (the claim of one is taken back), a cloth where the game reads none (the cloth is unlinked, its file stays) and a waiver with no reason or no rule (it is removed); a garment with no ped or slot is not given one. The code of a rule is a field of its finding and no part of its sentence, so a screen and the problems of a plan say what is wrong in plain words, without the code, a backtick, the word module or output, or the garment's name twice (`every_rule_says_what_is_wrong_in_a_plain_sentence`). A texture or a cloth that is named and is not there is not a remedy of a rule but an edit of the pack: the screen offers Locate…, which copies the file chosen into the pack, and Remove, and neither a waiver, since no reason mends a file that is not there.
- **Limits and configuration.** Wave P23 holds a pack to what its files state, and a project decides how hard. `or_wardrobe::measure` counts each model and texture dictionary as its bytes are read, at `Depth::Measure`: the size, mips and format of each texture, the levels of detail with their vertices and triangles, the shaders that bind no diffuse texture, the textures a drawable carries that none of its shaders uses, and the pages the game streams for the file, which its RSC7 header states (`a_dictionary_is_counted_texture_by_texture_as_it_was_built`, `the_models_of_the_corpus_are_counted_level_by_level_as_their_reader_states_them`). The count is kept with the digest, so a file that did not change is not counted again, and a file the owned readers do not open has only its pages and is not judged. Twelve rules read the counts: `texture-size` (2,048 pixels on a side), `texture-not-power-of-two`, `texture-mips` (a texture larger than 4 by 4 pixels that stores a single mip), `texture-format` (a format other than DXT1, DXT3, DXT5 and DXN), `texture-bc7-legacy` (BC7, which a DirectX 10 card cannot read, in a pack built for Legacy), `dictionary-size` (16 MB of streamed memory), `lod-missing`, `lod-medium-heavy` (a medium level with more than half the vertices of the high one), `lod-low-heavy` (a low level of more than 500 vertices), `polycount-high` (35,000 triangles at the high level), `diffuse-missing` and `embedded-unused`. The engine enforces none of them, so each is a warning, which a project may raise to an error, except `lod-missing`, which is a note until a project raises it: 973 of the 1,946 garments of the reference pack, and 16 of the 25 staged ped component models of the game, have no medium or no low level, and the game does not need one. The limits that are ours are the reference pack's own figures, not the engine's (99 percent of 610 of its textures that were sampled are 2,048 pixels on a side or less, and 90 percent of its 1,982 drawables draw 33,291 triangles or fewer at the high level), and the 16 MB is the figure of the clothing tools this one is compared with, which no constant of the engine states. A garment with several textures at fault is one finding that counts them and names the first, so a pack of thousands is a list a person can read (`each_texture_rule_finds_the_texture_built_to_break_it_and_only_that_rule`, `each_rule_finds_the_texture_file_built_to_break_it_and_a_clean_one_is_silent`, `a_garment_with_many_textures_at_fault_is_one_finding_that_counts_them`).

  A pack's `wardrobe.json` holds `rules`: the edition it is built for (`legacy` or `enhanced`, and both where it says none), which decides the limits that depend on it, and for each rule a reason could already set aside, whether it is on, how serious it is and where its limit stands. A rule no reason mends cannot be switched off or softened, and what a pack sets that changes nothing is a warning of its own, `setting-unheeded` (`a_rule_the_pack_switches_off_finds_nothing_and_one_it_raises_stops_a_build`, `what_a_pack_sets_that_changes_nothing_is_said_and_changes_nothing`). The list of rules, with each severity, whether a waiver can set a finding aside and each limit with its unit, is `or_wardrobe::rules::export`, which `openrage-cli wardrobe rules` and Export the list… write and a test holds equal to `RULES` row for row (`the_list_written_out_reads_back_as_rules_row_for_row`). The plan states four figures beside the drawables and textures, which the strip shows against the ceilings a build declares: the shop entries, the entries of an archive (the files and the folders they sit in), the size of the metadata it writes and an estimate of the memory the game streams for the files it copies (`the_plan_counts_the_metadata_the_shop_the_archive_and_the_memory_of_what_it_ships`).

  What a session read of a pack is kept in the pack's private folder (`or_wardrobe::cache`, `.openrage/files.json`, which ignores itself), for a pack this project edits that no other window holds the lock of, only once more than 200 files were read and only when a scan read a file since the last time it looked (`a_scan_that_read_no_file_keeps_nothing_again_and_one_that_read_a_file_keeps_it`, `a_window_another_holds_the_pack_of_keeps_nothing_in_it_and_keeps_what_it_read_once_it_is_free`), and the next session reads only the files whose size or time changed. Measured over the reference pack, 1,946 garments and 13,333 files of 3.9 GB, in a release build: 9.6 s the first time, with the files read and counted by up to eight threads, and 0.14 s and no file read the next time (`the_pack_of_a_server_is_counted_once_and_then_read_by_what_changed`). Over 5,000 garments of 10,000 small files built for the purpose it is 0.42 s and 0.29 s, and one changed file is the one read (`a_pack_of_five_thousand_garments_is_counted_once_and_then_read_by_what_changed`). In the dev profile, which builds with Cranelift, the same two runs took 197 s and 0.22 s, and 2.9 s and 1.0 s.

  The limit of alternates is built since P27 typed the alternate-variations metadata: a garment that makes more drawables change than the game holds for it is the error `alternate-limit`, and the typed root refuses one switch past that (under Behaviour, alternate variations and the first person, below).

  Not built, because nothing the pack states or its files measure says it: the pool of texture dictionaries and the number of `.ymt` files a ped loads by game build are the game's own configuration, a misnamed embedded texture and illegal characters in the name of one have no name the game refuses, and the caps of hats and props are not a pack's. The cap of drawables per slot is built since P29 ([capacity](#capacity), below).

- **Verifier.** After a build, the variation metadata of each ped is read back and held to the garments (a drawable for each, with its textures and one component info), the creature metadata to the plan, the shop metadata entry by entry to the ids the plan wrote (a count that agrees with the wrong ids fails), and the collection to the one claimed. It checks the files and not the game; nothing here says a pack loads. - **Heels and hair.** An expression is kept as the engine states it. The staged creature file of a server adds, for each of 88 feet drawables, an entry for expression 4 with one track, one id, one type and one component, while the component infos of those drawables state no expression modifier. A heel is no field of the engine's but two statements together, which `or_wardrobe::heels` reads and writes: the fifth of the feet drawable's `pedXml_expressionMods`, and expression 4 for the same drawable in the creature metadata. Over the 1,832 staged variation documents, 174 feet drawables state a value in the fifth modifier and nothing in the other four (156 state 1.0 and 18 state -0.075), and 206 feet drawables state expression 4 in the staged creature files, 199 of them as one track (33), one id (28462), one type (2) and one component (1), and 7 with the id 15570; the engine writes the 199's shape (`a_staged_heel_states_its_value_in_the_fifth_modifier`, `the_expression_a_heel_is_written_with_is_the_one_staged_feet_drawables_state`). What the value is for the game, a weight or a height in some unit, is not measured: the owner's Vestium notes record that the game's own heels state 1.0 where two tools write 0.2 to 1.5 and 0.1 to 1.7. The preview raises the ped by a tenth of the value, which is how Durty Cloth Tool and grzyClothTool draw it and is a convention of the view and no measurement (`the_heel_flag_raises_the_ped_by_its_stated_height`). Hide hair is a preset of the hair scale (the Hair bullet below) and hide ears is not built: no source this build has names a bit of `flags` or `propFlags` for hair or ears, the community's list of ten behaviour flags has none, the staged `inclusions` and `exclusions` hold masks whose bits nothing here names, and the owner's Vestium notes put hiding a hair under a mask or a hat in alternate models, which is the alternate-variations metadata that wave P27 types (below). What the staged creature metadata does drive for a hat is the hair scale, and for a hair its height, which P27 names.
- **The dressed ped's query.** `or_wardrobe::dress::dress` takes the pack, a choice (the ped, the garments worn in the order they were put on with the variation of each, a skin tone, whether heels count, and whether this is the original) and the ped's `BaseOutfit`, drawable 0 of each component slot its variation metadata states with the skin its first texture states, and says which model and texture each slot wears, the garments that are not worn with the reason (the other ped, a prop, a place held, a slot a later garment took), the slots a hat that states the hide hair scale takes off, and how high the heels raise the ped. The choice may also carry what was asked of the ped's own slots, `BaseEdit::Off` or one of the ped's own drawables (a drawable the ped does not have is no edit), and a garment worn in a slot comes first (`a_slot_of_the_peds_own_is_taken_off_or_wears_another_of_its_drawables`, `a_garment_beats_an_edit_of_its_slot_and_a_head_keeps_its_tone`); the `BaseOutfit` now holds every drawable of each slot with the `texId` its first texture states and says how many there are (`the_base_says_how_many_drawables_each_slot_has`). It touches no file and no renderer, so a test holds it to the pack (`for_a_reference_pack_the_query_selects_the_drawables_and_textures_its_slots_state`, `wearing_a_garment_changes_exactly_its_slot_and_the_original_is_the_ped_without_the_pack`); the files the base names are the ped's folder in `streamedpeds_mp` (`or_title::install::freemode`), `<slot>_000_<u or r>.ydd` and `<slot>_diff_000_a_<word>.ytd`, and its heads come two to a tone (`a_tone_chooses_the_base_head_and_its_texture_and_leaves_the_body`). The tone chosen only picks the head worn when none is asked for: a head asked for by its number is a race model that wears the tone its own first texture's `texId` states (1 white, 2 black, 3 Chinese, 4 Latino, 5 Arab and 10 Pakistani, which all 46 heads of each freemode ped of a Legacy install name their textures by), and every drawable the Ped's own menu offers is a model and a texture the install holds (`every_head_of_the_peds_own_is_a_race_model_whatever_tone_its_texture_states`, `a_head_asked_for_wears_the_tone_its_own_texture_states_and_not_the_one_chosen`, `every_drawable_the_peds_own_menu_offers_is_a_model_and_a_texture_the_install_holds`, `a_head_of_the_peds_own_that_the_menu_offers_is_drawn_and_no_file_of_it_is_missing`).
- **Replacing a texture.** `or_wardrobe::replace::texture` makes one variation's texture from an image or a `.ytd`: the picture is authored, or the file decompiled, into a textures source of the pack that the variation names in place of the old texture, which is not touched (`a_picture_replaces_a_texture_as_an_authored_source_with_no_dds`). The pictures an editor saves are the pictures of that source and the live recook of the source is the cook that follows a save, so no image sits beside a compiled texture and no scan remakes one. The tint and the flags of the variation stay (`a_replaced_texture_keeps_its_tint_and_flags_and_no_other_texture_changes`), a replacement that cannot be made changes nothing and says why (`a_replacement_that_cannot_be_made_changes_nothing_and_says_why`), and a texture replaced from its row is one click from Undo (`a_texture_replaced_from_its_row_is_one_click_from_undo`). A build cooks the source and ships the texture, for either edition from the one source (`the_same_garment_is_built_for_legacy_and_for_enhanced_from_one_source`).
- **Sources and references.** Wave P33 made the pack hold sources: a model, an alternate or a texture a garment names is a `.drawables.src` or a `.textures.src` folder, or a reference (`.ref.json`, [what references build](Project_Model_Design.md#what-references-build)) to a source or file of this project or of another, or an id alone. `follow` leads the name to what it names, the facts and the rules read what that leads to (a reference that leads nowhere is a Problem that says where it looked), and `plan` cooks a source with the cook a build uses and moves it to the edition the build ships, so one source builds for Legacy and for Enhanced (`a_texture_source_and_a_model_source_of_the_pack_are_read_as_the_files_they_become_and_cooked`, `a_reference_leads_a_model_and_a_texture_to_sources_of_the_project_and_follows_a_rename`, `a_reference_to_a_source_that_is_gone_is_a_problem_that_names_where_it_looked`, `an_id_alone_builds_with_a_plain_sentence_and_ships_no_file`). `intake` is the one door: every game file a drop, Add clothes, Replace or Add texture brings is decompiled at once, and a file it cannot decompile is left out by name with the reason. A pack adopted from disk is read in place with the compiled files it holds, and a part replaced in it is replaced by a source; the cloth, which has no source form, stays a compiled `.yld`, and the shop's carried files stay as they are.
- **Fix all safe and the optimiser.** Wave P24 adds `or_wardrobe::fix::all_safe`: a pipeline of repair, textures, order and mask, each step reporting what it changed and what it refused, as one `Revision`, with the findings it leaves standing and why. What it does is what changes no picture on purpose and takes no garment out. Repair is the policy of 2026-10-03 (a count is rewritten from its run only when asked, and only where that loses nothing): a compiled model whose counts contradict their runs becomes a drawables source made of the repaired file, the sentences of the repair are kept in the source's `asset.json` and the report, the file it was is not touched, and an `FXAP` file is refused by its name (`asked_to_repair_it_the_model_becomes_a_source_with_the_report_and_the_file_stays`, `a_protected_model_is_refused_by_name_and_the_repair_of_its_garment_says_why`). Textures is `or_wardrobe::textures`, which hands each textures source to `or_source::optimise`: the nearest power of two, a missing chain of mips, BC1 or BC3 by alpha for a texture stored uncompressed (and for BC7 in a pack built for Legacy, which a DirectX 10 card cannot read), and, only when asked, a size cut by a ratio or to a longest side. Only the DDS of a texture that changes is written, and it is written the cheapest way that keeps the artist's blocks: the mips are added under the level that is there, a halving drops the top levels and keeps the rest, and only a change of size or of format is encoded afresh (`a_texture_that_stores_one_mip_gets_its_chain_and_keeps_the_blocks_it_had`, `a_ratio_or_a_side_drops_the_top_levels_and_keeps_the_others_as_they_were`); the compile then copies that DDS block for block. A source is copied and the garments name the copy, so Undo takes the copy out (`the_garments_asked_for_name_a_lighter_copy_and_the_source_stays_as_it_was`), and a picture-made texture, a compiled `.ytd` and a reference are left and listed. Order is the finding's own remedy applied to every clash and every pin past the end of its slot. Mask is the remedy of `mask-skin` applied to every stated mask that disagrees with its garment's skin by the skin bit alone; one that asks for the match form stands, with why (`fix_all_safe_mends_the_skin_bit_says_what_stands_and_a_second_run_changes_no_byte`). Run twice, the pipeline changes no byte (`it_clears_what_it_can_says_what_stands_and_a_second_run_changes_no_byte`). `openrage-cli wardrobe fix` and `wardrobe textures` run the same.
- **Class sizes.** The cloth class has 24 bytes in each of the 1,832 staged variation documents and a table made from its one member alone has 1, which moves every class that holds it. The ped family's types are declared with the bytes no member names, and a table written for a record built from nothing is the table every shipped document has, signatures included (`a_variation_built_here_carries_the_table_every_shipped_one_does`), so whether the game minds a changed size does not arise for these classes.
- **Selection sets.** A set built here dresses no slot, with 255 for none in `compDrawableId` and in `compTexId`. - **The creature metadata** of a pack is one RBF document both peds share, and a record built from nothing is written as RBF: 56 of the 64 staged RBF documents come back byte for byte from a record built out of their values, and the other 8 hold an empty tag (7) or add the tags in another order (1), which a record has no member for.
- **Cloth.** A garment's `cloth` is the `.yld` of its model, shipped under the model's name beside it (the staged game's cloth files are named as the drawables they belong to, such as `cs_josh_uppr_000_u.yld`, and the owner's Vestium ships a component's cloth under its model's name; no staged drawable sits beside its cloth to be paired, so the pairing is held to that and not measured here). It is the garment's child and not a thing the garment declares: a garment has cloth when one is linked, and the build writes `ownsCloth` from that, so neither the model nor the Garment panel has a flag to edit. Link and unlink are edits with Undo (`linking_a_cloth_turns_the_flag_on_and_unlinking_turns_it_off`, `a_cloth_is_linked_to_the_garment_selected_and_unlinked_and_undo_takes_each_back`); a prop owns none and a place held has no model to name it after, so neither takes one. An import keeps the cloth the metadata states, so a pack imported from a resource rebuilds with its cloth (`a_pack_imported_from_a_build_rebuilds_with_its_cloth`), and lists a garment whose metadata states `ownsCloth` with no cloth file as missing its cloth until one is linked or a waiver gives a reason (`a_garment_that_states_the_flag_with_no_cloth_is_listed_until_one_is_linked_and_undo_lists_it_again`). A cloth beside a model whose metadata does not state the flag is not linked, since linking it would make the game simulate what it did not; that waits for a real pack to show what the game does with a cloth shipped that way, which nobody here can run, and the server's resource ships none. Link in the Garment panel does it by hand. `.yld` is copied unchanged for an Enhanced output, since neither install ships one to retarget.
- **Durty-compatible shop names.** `shop.durty_hashes` of the pack, off by default, names each shop entry that states no id as Durty Cloth Tool does (`CLO_DCT_TOP_0_0_M`, `CLO_DCT_PROPLWRIST_2_1_F`); an id an import read, or somebody chose, is written as it is. - **A model that is a source.** A garment's `model` may name a `*.drawables.src` folder inside the pack's folder instead of a `.ydd`: the plan ships the file the build cooks it into under the name any model of its place has, and never the folder (`a_garment_that_names_a_source_folder_ships_the_cooked_file`). It is looked at as the file it becomes (its size is what the cook reads, its digest is the folder's, so an edit of the source is an edit of the garment for the build's diff), a source the build cannot cook is a model that does not open and says why, and it is never left out as the game's own file, since the metadata states the drawable. The Files content, which holds every other `.src` folder of the project, leaves it to the garment, so one source is not cooked twice (`the_files_content_cooks_its_own_sources_and_leaves_the_one_a_garment_names_to_the_garment`). A source copied from outside the pack, or with a garment, gets an id of its own, since two sources with one id cook into one file. The dressed ped cooks the folder on its worker to draw the garment, and reads it again when a file inside it changes (`a_source_folder_is_stamped_by_what_is_inside_it_and_a_folder_that_cannot_be_cooked_says_why`), and `openrage-cli wardrobe build` hands the build the same cook.
- **Not built:** a garment that names a `*.textures.src` for a texture, which H2's choice leaves as a `.ytd` with the image beside it. The screen over the engine is [what the Wardrobe workspace builds](Workbench_UX_Design.md#what-the-wardrobe-workspace-builds).

- **Reopening a built pack and exchanging garments.** Wave P26. `or_wardrobe::reopen::reopen` reads a singleplayer DLC, an `.oiv` or the folder that holds one (`or_project::built::unpack` hands over each file, the archives inside a pack opened, and tells the files an `.oiv` installs outside its pack from the pack's), lays the clothing out as the resource the import reads, and makes a project of it: a clothing content in which every model and texture is a source, as a dropped file is (a cloth has no source form and stays compiled), with the garments pinned at the numbers their names carry and everything the variation, creature and shop metadata state. - **Props worn, wind, shop entries, the heaviest outfit and what a reopened pack has broken.** Wave P34. `or_wardrobe::dress` answers for props as it does for components: `Dressing::props` holds the garment worn at each anchor, in the order of `Prop::ALL`, and the preview carries it to `Prop::bone`; `Choice::alternates` makes a garment wear the alternate model of a number it has (`dress::garment_by`). `Garment::wind_scale` is the scale the plan states in every cloth of the linked `.yld` (`or_wardrobe::wind`): the plan replaces the copy of the cloth by a generated file stating it, the cloth file linked is never written, the digest of the garment covers it, and the verifier reads the shipped cloth back and names a build whose cloth does not hold it (`the_verifier_reads_the_shipped_cloth_back_and_names_a_build_that_does_not_hold_the_scale`). All 58 shipped cloths state exactly 1.0 (`the_wind_of_every_shipped_cloth_is_read_and_stated_again`), which is the default of the controller, so the range a person may state is a sanity bound and no measurement. `or_wardrobe::shop_edit` edits the entry of one texture (`Edit::Shop`): the price, the restriction tags and the forced components are typed because the staged shop files state those and no other element (`the_staged_shop_files_state_only_the_elements_the_editor_names` reads every entry of the reference pack's two shop files and states each one's forced components and tags again as it was), and any other element is kept and edited as the XML it is written in (`Field::Raw`), a lock hash, the variant components and the outfits among them. An entry made by an edit has no id (`ShopEntry::id` and `from` are empty then) and is dropped when it states nothing. `or_wardrobe::outfit` takes the pages each file states in its header for the heaviest garment of every slot of a ped (the model, the cloth and the heaviest texture), and the plan states the heaviest ped's as `clothing_outfit_memory` beside `clothing_slots` and `clothing_props`, which together are `clothing_drawables`. `Reopened::broken` is the errors and warnings of the rules over the pack a reopening made, with the files opened through their readers.
- **Extension.** A validator and an emitter are plugins that read the plan this engine contributes to and hand back findings and text files, with nothing else crossing ([what the extension builds](Project_Model_Design.md#what-the-extension-and-the-second-kind-of-content-build)). The cloth physics half of [R46](Roadmap.md#r46-first-plugin-a-clothing-tool-on-openrage) is `plugins/cloth-painter`, a plugin over a garment's `.yld` ([plugins/README.md](../../plugins/README.md#the-cloth-painter)); the pack tool stays first-party, as principle 7 says. The second kind of content, the addon ped, shares what this engine and it both needed through `or_project::content`.

## Decisions asked of the owner

1. **Amend R44f?** The pack tool is first-party; R46 narrows to cloth physics and stays the plugin reference case. Recommended: yes.
2. **Typed ped metadata in or-io**, as OD-META-TYPED allowed for the world family. Recommended: yes.
3. **Order of targets.** FiveM first (largest audience, loose files), then singleplayer. Recommended: FiveM first.
4. **Durty-compatible shop hashes** so existing shops and packages survive a migration. Recommended: an option, off by default.
5. **Name and presentation.** A Wardrobe workspace in OpenRage, with a start-page tile; a standalone flavour binary only after wave 3. Recommended: workspace first.
6. **In-game verification.** Who runs GTA V for the first packs, or whether a community tester cohort is recruited.
7. **Price and openness.** Free and open is assumed; say if not.
