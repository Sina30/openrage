# Shader pipeline design

How OpenRage runs the original compiled shaders of GTA V Legacy, GTA V Enhanced and Red Dead Redemption 2 natively on Windows, Linux and macOS (Metal).

Status: planned. The owner approved the plan on 2026-10-07 ([the decision](Project_Context.md#game-shaders-are-translated-once-to-spir-v-and-run-natively-on-each-os-2026-10-07)); of it only the `inventory` command exists, in `crates/tools/or-shader-tool/src/inventory.rs`. [R58f](Roadmap.md#r58f-shader-baking-off-windows) tracks the work.

## Verdict

One new translator, from each game's bytecode to SPIR-V, runs in a helper program during a bake and is never loaded by the editor. SPIR-V is the pivot every OS consumes: Vulkan takes it as it is, and Metal and the DirectX 12 fallback take it through naga inside wgpu. The pack becomes a cache of SPIR-V and reflection data. The renderer follows the game's own binding, vertex and state rules instead of the editor's fixed ones. The goal is the whole frame, reached in rungs, with the material preview first.

## Why a translation is needed

| API | What it accepts |
|---|---|
| Direct3D 11 and 12 (Windows) | DXBC, and DXIL on Direct3D 12 |
| Vulkan (Linux, Windows) | SPIR-V only |
| Metal (macOS) | Metal source or a compiled metallib only |
| wgpu, the renderer | WGSL or naga IR; passthrough takes SPIR-V on Vulkan, DXIL or HLSL on DirectX 12, and MSL or metallib on Metal, with no DXBC input |

The games ship Direct3D bytecode, so no API on Linux or macOS can load it, which is why Wine, DXVK and Apple's own toolkit all translate. Running it untouched on Windows means a second, Direct3D-only renderer, the way CodeWalker draws, or wgpu's DirectX 12 passthrough, which builds its own root signature and cannot match the one a game's DXIL carries. A translated shader is game-derived and is never shipped: each user translates their own files, so the translator ships with the app.

Rejected, with the reason:

| Alternative | Why not |
|---|---|
| Slang as the pivot | It compiles Slang or HLSL source and has no bytecode input that was found, so it would sit behind today's lossy decompiler. SPIR-V already serves every renderer through SPIRV-Cross, naga and Tint. Slang stays open for the editor's own shaders, a separate decision. |
| DXIL as the pivot | DXBC needs the Windows-only `dxilconv`, and Apple's Metal Shader Converter is proprietary, takes DXIL only and binds through argument buffers that wgpu's Metal backend does not use. |
| A DirectX 12 pipeline outside wgpu | No conversion on Windows only, in exchange for a second renderer and the whole-frame work done twice. |
| A CPU interpreter of the bytecode | Far too slow for a viewport. |
| Porting each effect to WGSL by hand | It is not the game's shader, and each title declares its own long list of effects ([Shader_Definition_Database.md](../features/Shader_Definition_Database.md)). |
| The old chain, now removed | DXBC to HLSL text by a Windows decompiler, then DXC, naga and a text patch: four steps, two of them Windows programs, and the coverage was in [Viewport_Shading_Modes.md](../features/Viewport_Shading_Modes.md). |

## What is known

| Game | API and bytecode | Container | Stages |
|---|---|---|---|
| Legacy | Direct3D 11, DXBC shader model 4 and 5 | `.fxc` in `common.rpf`, replaced and added to by `update/update2.rpf`, read through the game's mount by `crates/title/or-title/src/install/shaders.rs` and parsed by `crates/io/or-io/src/gta5/shaders/fxc/grc_effect.rs` | vertex, pixel, compute, geometry, hull, domain ([CodeWalker's reader](https://github.com/dexyfex/CodeWalker/blob/master/CodeWalker.Core/GameFiles/FileTypes/FxcFile.cs)) |
| Enhanced | Direct3D 12 only; DXIL shader model 6 with a root signature per shader, per third-party tool READMEs ([shadermanager](https://github.com/crxhvrd/gta5-shadermanager)), unverified here | `sga_win32_60_final` and its `_init` sibling, read by `crates/io/or-io/src/gta5/shaders/sga.rs` for the definition database only | the same six, per those READMEs |
| RDR2 | Both renderers ship; the DX12 shaders are DXBC shader model 5.1 ([RenoDX port](https://github.com/jakeypiez/rdr2-renodx-dx12)); the Vulkan ones are probably SPIR-V, unverified | the sga_vulkan_final and sga_win32_60_final archives, which the tree cannot open yet ([R56](Roadmap.md#r56-rdr2-the-second-container)) | compute-heavy; tessellation likely, geometry unknown |

A DXIL shader sits in a container that opens with the same `DXBC` tag, so the tree's magic check cannot tell the two apart. `or-shader-tool inventory` reads the parts, the program version and the feature flags of every container, and the capabilities of any SPIR-V module, so the formats above are settled by running it on each install before a front end is chosen for them.

## The pipeline

- **Front ends.** `dxbc-spirv` (MIT, shader model 5.1 and older, the translator DXVK 3.0 uses) takes DXBC; `dxil-spirv` (MIT, from the vkd3d-proton author) takes DXIL and, through dxbc-spirv, DXBC. Both are C++, vendored and compiled by cargo with the `cc` crate, with no CMake, Meson or download, behind a thin C interface in `crates/tools/or-shader-front`. dxbc-spirv is in, behind the crate's `native` feature, which is off until a Windows build is checked; dxil-spirv is not. Only the `or-shader-tool` binary will depend on it. The app starts that binary as a background job and reads its progress as JSON lines; the editor process holds no C++, a crash in the translator cannot reach it, and the frame loop never calls it. A game's own SPIR-V skips this step.
- **Mapping.** Bindings and interface locations are decided as the translator writes the module and not by editing the output text. A binding is a function of the register and the stage alone (`BindingLayout` in `crates/tools/or-shader-front/src/layout.rs`), so it needs no per-blob map: Direct3D 11 keeps a table of slots for each stage, so a pixel shader's registers are in the set after a vertex shader's, each register space steps the set by two, and each class of register has a window of bindings in a set (constant buffers 0 to 15, samplers from 16, resources from 32, unordered access views from 160, their counters from 224). Reflection (`RDEF`, the signatures, `PSV0`, `RTS0`) names what the layout places and checks it, as [measured below](#where-each-register-binds).
- **The pack.** Pack version 3 is a content-addressed cache keyed by the blob's hash, the front-end version and the mapping version, and by title and build. It holds SPIR-V and a reflection manifest, with WGSL as a debug export. A bake is incremental and parallel, and a game update translates only the blobs that changed. `or-shader-tool bake-pack` writes it, as [measured below](#what-a-bake-writes).
- **The backend per OS.**

| OS | Backend | Path |
|---|---|---|
| Linux | Vulkan | the pack's SPIR-V by wgpu's `PASSTHROUGH_SHADERS` |
| Windows | Vulkan, if the measurement agrees, with DirectX 12 as the fallback for a machine without a Vulkan driver | SPIR-V by passthrough, or the naga path below |
| macOS | Metal | naga's SPIR-V reader with its own options, because `ShaderSource::SpirV` fixes strict capabilities, then the legalizer, then naga's MSL writer |

Metal is native: wgpu's Metal backend, with no MoltenVK, Wine or D3DMetal. Passthrough skips wgpu's validation, so the helper validates each module with SPIRV-Tools before it enters the pack. If the measured naga rejections justify it, Metal takes MSL that SPIRV-Cross wrote during the bake, as passthrough; wgpu then assigns Metal slots itself, so the mapping has to reproduce its order.

## The renderer side

Translating a shader is not using it. At the start the drawable pipeline fixed its vertex layout and two bind groups, took blend, depth and cull from a name-prefix table while the parsed pass states went unread, and supplied none of the game's constant buffers. The renderer's second ABI replaces each of those:

- **Bindings** from the register layout, where the first ABI's tables were fixed, with the names and kinds each blob's reflection gives them.
- **Vertex input** from the input signature and the effect's vertex type, uploaded from the drawable's own vertex declaration, with locations the first ABI fixed by semantic.
- **Render state** decoded from the effect's pass parameters. Their (type, value) enum is undocumented, so it is derived from the Legacy files and frame captures and pinned by golden tests; the name table stays as the fallback.
- **Engine constants** filled by variable name from the camera, the time of day and the lights.
- **A frame recipe per title**: the passes, technique names and target formats, because pass order lives in the executable and not in the shader files. It is taken from the game's own frame code, which the owner allows to be ported ([2026-10-08](Project_Context.md#the-game-source-may-be-ported-and-a-comment-never-says-so-2026-10-08)), and checked against captures and the retail behaviour.

Fidelity rungs, each shown with `just shots` before and after: forward `draw` techniques; the deferred G-buffer writers with the game's lighting shaders; shadows and lights; the post chain and sky; particles, water, terrain and vegetation; then each title's extras.

## Lowerings and missing stages

The legalizer adapts what naga or a backend rejects, and each lowering has a test that fails without it: the early-depth attribute is dropped where Metal and DirectX 12 reject it; clip and cull distance become `discard` on Metal; typed buffers and format-less UAVs become storage buffers or take a format from reflection; derivatives in non-uniform control flow are hoisted, because wgpu validates uniformity with every flag; texture counts above the default limit raise the limits.

wgpu has no geometry, hull or domain stage on any backend. The viewer does not need them: a pass binds a hull or domain stage only in a technique variant that asks for tessellation, and a geometry stage only in an instanced draw or the bokeh post effect ([measured](#what-a-pass-needs)), while the plain vertex-and-pixel techniques a material preview draws carry neither. They stay out until a feature needs one, and the design for it is compute emulation, one for all three OSes: a tessellation prepass into a vertex buffer, and geometry expansion with an indirect draw.

## Fidelity

- **Lossless**: reflection is copied into the manifest unchanged, the exact SPIR-V module reaches the driver on Vulkan, and the pack is a cache of the user's own files, so a translator fix re-bakes and nothing is destroyed.
- **Near-lossless**: bytecode to SPIR-V is a compile, instruction by instruction, with no decompile-and-recompile. Floating point is equivalent within a measured tolerance and not bit-exact, because GPUs differ in transcendentals and denormals for the game itself too. The first spike checks that `precise` becomes `NoContraction`.
- **Approximated, and labelled**: every lowering above, hull, domain and geometry emulation, and decoded state and constants. The manifest records `fidelity` as exact, equivalent or approximated, with the lowerings per shader, and the coverage report counts each class.
- **The oracle** is the original bytecode run by Direct3D on the owner's Windows machine, in a test harness that is never shipped, against the same inputs through this path. Image differences are recorded in the Roadmap with suite and revision.

## What the first spike measured

On macOS, dxbc-spirv at `c7f06970` compiles with plain `clang++` and no build system, and `or-shader-front` compiles it through cargo's `cc` crate. At `47597854` with this change, `or-shader-tool translate-check` (its `native-front` feature) translates every DXBC container of a Legacy install's mount, 35,468 of 35,468 across the main folder and the low-quality and stereo-3D ones, with none refused. Raw, none is readable by naga: its strict reader refuses the physical-pointer capability every module declares. The legalizer (`crates/tools/or-shader-tool/src/legalize.rs`) drops the Vulkan memory model and physical pointers, turns the compute shaders' `LocalSizeId` into `LocalSize`, turns each demote into a kill (which ends the invocation where a demote would keep it running as a helper, and so changes only what later derivatives see), makes clip and cull distances private because the device offers neither (they no longer clip, an approximation the legalizer counts, and a discard in the fragment stage would restore it), and gives each interface location one variable: the translator splits a register's components into variables that share a location, which naga cannot express, so the legalizer replaces them with private copies and a vector variable that the entry point copies into them on entry, or fills from them before every return, wherever their type and interpolation agree, which was every case.

The translator's own options remove most of the rest, and the shim sets them: constant buffers as vector arrays, structured buffers as nested arrays (`structuredCbv` and `structuredSrvUav` in its resource options), no rounding or denorm modes, and float-to-integer conversion as a native instruction, because a call to a helper function trips naga's Metal writer. With its defaults, a local run at `2884a9b5` over the main folder's 11,853 modules wrote 6,175 as MSL and the uniform layout rule stopped 3,263 of the others, because a D3D constant buffer packs a vector at any four-byte offset in a register and its typed struct is not valid std140.

`or-shader-tool translate-check` then reads each module with naga 29.0.1, validates it against every capability and writes MSL for Metal 3.0, and with `--device` (the `device-check` feature) builds a pipeline from it on the machine's own GPU, which runs Apple's shader compiler over what naga wrote: a vertex shader gets a buffer layout from its inputs, a fragment shader a generated vertex stage that outputs what it reads, a compute shader a compute pipeline. At `47597854` with this change, on an Apple M4 Pro, it reads 32,552 of the 35,468, validates 30,439, writes 30,304 as MSL and **30,217 compile on the device**, in a minute and a half:

| Stage | Modules | Read | Validated | MSL | Device |
|---|---|---|---|---|---|
| Vertex | 13,186 | 13,186 | 11,152 | 11,152 | 11,152 |
| Pixel | 19,366 | 19,330 | 19,287 | 19,152 | 19,065 |
| Compute | 132 | 36 | 0 | 0 | 0 |
| Hull, domain, geometry | 2,784 | 0 | 0 | 0 | 0 |

At `47597854` with this change the rest stop at a few causes, each with its fix. The hull, domain and geometry stages (2,784 modules) have no stage in naga, which no legalizer fixes and compute emulation answers. Vertex shaders with no position output (1,992) feed those stages. naga's own Metal writer panics on 135 modules and writes source that Apple's compiler refuses for 87 more (a lod variable used outside its scope), which are naga's to fix. Smaller causes remain: storage-image writes with no format (96), an integer negate (42) and write-only storage buffers (36).

⚠ These are measured on one device, whose limits the run takes whole; the raw output is not yet offered to a Vulkan driver, and the DXIL front end, the Windows build with MSVC and the Linux build are untried. `cargo run -p or-shader-tool --features native-front,device-check -- translate-check <install> --device` is the command, on any OS with a GPU.

## What a pass needs

A module is not what a viewer draws: a pass of a technique binds a vertex program and, usually, a pixel program, and it draws only if every program it names builds. `or-shader-tool pass-check` reads each effect, takes the programs its passes name by their one-based position among their stage's programs, and builds each on the device. At `15bef620` with this change, on the same Apple M4 Pro, over the 375 effects of the Legacy install's `win32_40_final` folder (none unreadable) and their 11,853 programs, 10,093 build, and the 14,876 passes fall by the stages they bind:

| Stages a pass binds | Passes | Built |
|---|---|---|
| Vertex and pixel | 12,129 | 11,937 (98.4%) |
| Vertex only | 438 | 438 |
| Compute | 44 | 0 |
| Any hull, domain or geometry stage | 2,264 | 0 |
| Binds nothing | 1 | 1 |

At `15bef620` with this change, the techniques a material preview draws build almost whole: `draw` in 276 of 277 effects, `deferred_draw` in 216 of 216, `drawskinned` in 199 of 199, and the lightweight and water-reflection variants of each at or near all of theirs. What does not build is the 2,264 passes that name a stage wgpu lacks, which are the tessellated and instanced variants, and the 44 compute passes, which stop at naga's reader and validator. Counted per stage a pass binds, 3,793 stop at an execution model naga does not read and 1,885 at a vertex shader with no position output, which is the vertex stage that feeds a hull or geometry stage; the rest are naga's own limits (57 integer negates, 45 Metal-writer panics, 32 format-less storage images, 30 extension instructions, 29 uses of a lod variable outside its scope, 24 initializers it rejects, 12 write-only storage buffers and 6 demotes it will not read).

So for the viewer the stages left are not emulation but compute, such as light culling and luminance, which the compute phase of the plan takes.

## Whole pipelines

A pass whose programs each build can still fail to build as the one pipeline its stages make, because the pipeline is where one stage meets the other. At `161d6a20` with this change, `pass-check --device` builds each pass of a vertex stage and at most a pixel stage, once for each distinct pair of programs, on the same Apple M4 Pro: 1,996 of 12,375 passes build, from 5,768 distinct pairs. The per-stage numbers above hid it, and the rest stop at two causes.

- **Bindings (8,876 passes).** The layout gives a register the same binding in every stage, and in these pairs the two stages use one binding for different kinds of resource: Direct3D 11 keeps a separate table of slots for each stage, so a vertex shader's `t0` and a pixel shader's `t0` are two resources, and the layout makes them one. Each stage needs its own set.
- **Interface types (1,500 passes).** Metal refuses a pixel input whose type differs from the vertex output at its location. The signatures agree, since at `161d6a20` with this change 5,717 of the 5,720 distinct vertex-and-pixel pairs meet exactly by semantic, register and mask and the other 3 read a narrower mask, so a pair links by register. The modules do not: dxbc-spirv types a location by the components a shader uses, a `float3` where the other stage has a `float4`. And 3 passes fail on an interpolation that differs between the stages.

### Each stage has its own set

`BindingLayout::for_program_type` puts a pixel shader's registers in the set after a vertex shader's, and the shim takes the shader's stage from its own container. At `693ec247` with this change, 5,164 of the 12,375 passes build as pipelines, from the same 5,768 distinct pairs, and no pass stops at a binding. The Metal interface error is now the main cause, since it had been hidden behind the binding one: 7,152 passes, and 59 more stop at an interpolation that differs between the stages. The device run over single modules is unchanged, with 30,217 compiling, and so is the register agreement with the reflection, 35,456 of 35,468 containers.

### Every location four components wide

The legalizer takes each location a vertex stage outputs or a fragment stage reads, which one variable of fewer than four components held, to a four-component variable with a private copy for the shader body, so any two stages type a location alike whatever components each uses (`interface_locations_widened` in the pack's manifest). At `881bf219` with this change, **12,316 of the 12,375 passes build as pipelines** on the same device, from the same 5,768 distinct pairs. The 59 left stop at the interpolation that differs between the two stages, which linking the stages ends. Of the 4,970 distinct programs of that folder, 4,051 had a location widened, and the fidelity labels, how far naga got, and the 30,217 single modules that compile on the device are the same as before, since widening changes how a location is typed and not what the shader computes.

### Linking the stages

Direct3D declares interpolation on the pixel stage alone, so a vertex shader's own says nothing, and a pipeline refuses a pair whose stages disagree: a pixel input read flat or without perspective meets a vertex output left to perspective. Building a pass's two stages now first gives each vertex output the interpolation and sampling that the pixel stage reads its location with (`match_interpolation`, which edits the vertex module in place and so keeps the handle its body's expressions are typed with). At `fdff0ed9` with this change, **every pass whose programs built builds as a pipeline: 12,375 of 12,375**, from 5,768 distinct pairs, which are the 11,937 vertex-and-pixel passes that built by stage and the 438 that bind a vertex stage alone. The 192 vertex-and-pixel passes and the 2,264 that bind a stage wgpu lacks never reached this check, since one of their programs did not build. The link lives in the renderer (`game_shaders::link`), with the vertex layout and colour targets a pair's interfaces ask for (`game_shaders::pipeline`), and the tool's device check builds its pairs through them, so the renderer builds a pass the way the check proved.

### Drawn with stand-ins

`or_renderer::game_shaders` reads a baked pack (`pack`), reads what each module binds from the module itself (`bindings`), makes the layout of every set a pass uses from that and builds the pipeline with it (`pipeline::build_pass_pipeline`), makes a stand-in for each resource (`stand_in`) and draws one triangle, so the device validates every binding at a draw, which a build does not. At `95de47a2` with this change, over a pack baked from the same folder (`bake-pack`, then the `draw_pass_check` example of `or-renderer`), **12,375 of the 12,567 passes whose programs all translated draw**, from 5,904 distinct pairs. They are the passes that built as pipelines, and the draw adds that each of their bindings holds what its module asks: uniform buffers sized to their types, two-dimensional, array, cube and three-dimensional textures of float, integer and depth kinds, multisampled textures, filtering and comparison samplers, and storage buffers. The 192 that do not draw hold a program naga does not take, and stop where they did by stage: integer negates, Metal-writer panics, initializers, extension instructions and a demote.

### A first render

Constants arrive by name: `game_shaders::constants::Filler` writes a value as the variable of that name in the layout the game's own reflection gives its buffer, at the variable's offset and no further than its size. The `first_render` example of `or-renderer` fills the engine's shared buffers that way, binds a checkerboard where the pass samples a texture, writes each vertex of a quad for the inputs the vertex stage reads by their semantics, and draws a pass of a baked pack into a PNG. At `c7d3be4b` with this change, `default.unlit_draw` and `default_um.unlit_draw` of the Legacy pack draw a textured quad on the Metal device, 169,744 of 262,144 pixels in 296 colours, the size and place a 45 degree perspective gives it. Two things were learned by drawing: the registers of a matrix hold its columns, since the shaders dot a position with each register, and the UV animation of an unlit pass is two rows of three numbers (`globalAnimUV0` is 12 bytes), which four numbers each had been refused for. The lit passes drew black at first, and the reason was not the lighting: all zero fog parameters fog a lit surface to the fog colour, which is black, and a bisection over the variables found `globalFogParams` the only one. With `game_shaders::engine::EngineConstants` giving the camera, a sun, a flat ambient light and fog parameters of one, which keep a pass from fogging to black without their meaning being decoded, `default.lightweight0_draw`, `default.draw` and `default.lightweightHighQuality0_draw` draw the checker lit by the sun and the ambient, `default.deferred_draw` draws its albedo, and `default_um.lightweight0_draw` draws too, at `0fb89905` with this change.

### Every pass rendered with defaults

`game_shaders::quad::render_pair` is what `first_render` did, as a function: it finds each constant buffer by the name the game's reflection gives it and fills it from the scene, binds the checkerboard to each two-dimensional texture, writes every vertex input from its semantic, and returns the pixels of the first colour target. The `render_pass_check` example does it for every pass of a pack. At `acb099a2`, of the 12,567 passes of the Legacy folder whose programs all translated, 4,443 drew something onto the quad, and the list of what they lacked was short: no skinned technique drew, since a skinned vertex stage reads bone matrices that were zero and blend weights the quad did not have, and the alpha-clipped deferred passes discarded everything. Identity bone matrices (`gBoneMtx`, 255 matrices of three registers), a blend weight of one for the first bone, and a `globalFade` of one, which is how much of a surface the fade-out leaves (at a quarter, a pass draws a quarter of its pixels, in a pattern), took it at `c0df9b88` with this change to **8,975 passes that draw something**, 2,948 that draw nothing and 644 that do not render: 452 write no colour and 192 hold a program naga does not take. `drawskinned` now draws in 198 of 199 passes, `deferredalphaclip_draw` in 193 of 228, `draw` in 251 of 295 and `lightweight0_draw` in 234 of 252. What is left to draw nothing is mostly not a mesh's material: the shadow passes (`wdcascade_draw`, `ld_draw`, `spotCM`, `pointCM`) write depth and no colour, the post-processing and ambient occlusion passes read a screen the quad does not have, and the water refraction passes read a refraction target.

### Meshes with materials

`game_shaders::mesh` draws a mesh the way a material asks. Each surface takes the forward technique of the effect its material names (`select_pass` tries `lightweight0_draw`, `draw` and `unlit_draw`, and their skinned spellings for a skinned surface, in their bind pose), writes each vertex input of that pass from the surface by its semantic, fills each constant buffer by the names of the variables in the game's reflection from the material's values, and binds each texture the material has to the sampler of that name; a texture it lacks is grey. A drawable stores the hash of a parameter's name wherever no database names it, so a material's vector may be called `0x4620A35D`, and the renderer takes a parameter for the variable or the texture whose name hashes to it (`the_nearer_of_two_surfaces_shows_whichever_comes_first` draws two surfaces into one frame and `a_constant_and_a_texture_a_material_names_by_hash_are_set_and_bound` is the hash). A material also names its effect by hash, which the tool turns back into a name with the effects of the pack it draws with.

A `MeshScene` is that, prepared once: it builds each pair's pipeline for a `Target` (the format of the first colour target, and the format and comparison of the depth target), binds the resources, uploads the vertices and keeps the uniform buffers, so that a frame is `update`, which writes the each material's constants and then the engine's over them, and `record`, which draws every surface into a pass its caller owns. The target is a parameter because a viewport's is not the renderer's own frame: its colour is sRGB and its depth is reversed, one at the near plane, and `a_scene_draws_into_a_target_of_the_callers_format_and_depth_direction` draws into exactly that, `a_prepared_scene_takes_new_constants_each_frame` draws one scene with a sun for each frame, and a pass that writes a second colour target, as 592 of the 1,153 surfaces of a sample of 300 drawables use (at `4a7b6de8` with this change), is built for a pass of one attachment, where the device ignores what is written past it; a scene that left such passes out drew 48.5% of those surfaces instead of 99.8%. A scene made again after an edit takes the pipelines it needs from a `PipelineCache` that the viewport keeps for its pack and target (`a_scene_made_again_builds_none_of_the_pipelines_it_has_built`), so an edit does not pay again for a pipeline the last scene built. `render_surfaces` is a scene drawn into a `Frame`.

`or-shader-tool render-drawable`, behind its `render-drawable` feature, reads a `.ydr` or `.yft` and the `.ytd` of the same name beside it (and for a `.yft` the generic textures of `vehshare` and its worn, truck and army kin, found by name in the mount order, which hold the mud, the detail and the glass that every vehicle names: without them a vehicle has no mud on its sills and no detail on its metal), from a file or from an install through the mount, and with `--shaded` through the viewport's deferred passes (a fragment is drawn with its wheels at its wheel bones (the surfaces of `fragment_wheels`), `--ground` lays the ground of Shaded under the drawable and `--sun X,Y,Z` lights it as a day of noon with the sun in that direction, to see the shadow it casts, and `--effect`, `--texture` and `--vector` then draw only one effect or set one texture or constant on every surface, to see what a single input does: a vehicle's dirt level, which the effect declares at its dirtiest and the engine now sets clean, was found so, and so was the colour of a vehicle's underbody: a vehicle material's `matDiffuseColor` is a marker `(2, k, k)` for the vehicle's colour number `k` that the game replaces as the vehicle is made, and the interior marker `(2, 5, 5)` drawn as a colour is a cyan five times too bright, so the preview gives each slot a colour of its own; the constants of a material go by their names only while the install's own effects are read, which this tool does as the app does), extracts a scene with the exporter `mesh export` uses, and draws it into a PNG with a pack. ### Particle sprites, trails and models

The baked WGSL did not draw the sprites of a particle effect, and the pack does. The renderer took the first vertex program and the first pixel program of an effect, and at `0715a379` the first pixel program of `ptfx_sprite` and of `ptfx_model` is a failed record in the pack the old chain baked (it stripped bindings the shader still reads), so those two effects had no pipeline and drew nothing; only `ptfx_trail` loaded. Of the 12,567 passes of a vertex stage and at most a pixel stage, which is what `pass-check` counts, the old chain's WGSL has every stage of 2,842 and the SPIR-V pack all of them (the join of those passes with the old pack's blobs, by the SHA-1 of each container, over the same 375 effects).

`game_shaders::sprite` draws a sprite with a pass of `ptfx_sprite`, the technique the particle rule names (`shader_template_technique_name`, which the file states, so no technique is inferred from flags). The game's vertex stage reads only which corner it is, as two indices of 0 or 2 in `TEXCOORD3`, once per vertex, and everything else once per sprite from a second vertex buffer (`vertex_streams`): the position, the colour, the frame blend and the glow, the corners as `centre ± right ± up` through the xyz and the w of `TEXCOORD6` to `TEXCOORD8`, and each frame's cell of the atlas as `[u_min, u_max, v_min, v_max]` in `TEXCOORD10` and `TEXCOORD11` with `v_min` the top. That reading is from the decompiled stage and checked against the device: at `0715a379` with this change `first_sprite` draws a sprite of the Legacy pack on an RTX 4090 over Vulkan at the rows and columns the camera predicts (x 194 to 399 of 194.2 to 400.2, y 143 to 245 of 142.7 to 245.7, at 512 pixels) with a red-over-green texture red at the top, and a flipped `v_min` and `v_max` fails it. Of the 28 techniques of `ptfx_sprite`, 15 draw there and are oriented so; the 8 `_screen` and 2 `_Thermal` ones draw somewhere else, since they place a sprite in another space, the 2 `_proj` ones read the vertex number and are refused by name, and the lit, soft, normal-spec technique lands where it should and fails the texture check, for a reason not found.

In the viewport, at `0715a379` with this change, 34 particles of the concrete dust effect of `core.ypt` draw nothing without a pack and a soft cloud with debris with one, in Material mode and in Shaded, whose pass draws into the HDR target (`just shots`, the effect played at the timeline's fastest rate, the headless clock moving a frame by almost nothing). `game_shaders::trail` draws a trail the same way with a pass of `ptfx_trail`, whose vertex stage reads a position, a colour and a texture coordinate once per vertex (and a direction for a lit technique, which the renderer gives as the way to the eye), as a triangle strip. ## Where each register binds

The translator's own resource mapping hands out bindings in the order a shader declares them, so the same register could land on two bindings in the two stages of one pass. `or-shader-front` replaces it with the layout above, placed by the shim from a table Rust owns, and refuses a register past its window by name. At `b35e1384` with this change, `or-shader-tool translate-check` compares the descriptors each translated module decorates with what its container's `RDEF` says it binds, over the Legacy install's 35,468 containers: 35,456 agree exactly, 12 bind less and none differ. The 12 are constant buffers that the shader declares and its reflection lists and that no instruction reads, which the translator drops. Counters needed a rule of their own: an append, consume or counted unordered access view carries a second descriptor, which the reflection does not list and the layout puts in the counter window (21 containers). The same device run as before still compiles 30,217 modules and builds 11,937 of 12,129 vertex-and-pixel passes, so sparse binding numbers cost nothing on the Metal device.

⚠ A register space takes two descriptor sets, one for each stage, and wgpu offers four sets by default, so a shader model 5.1 title that uses more than two spaces needs the limit raised. The space path is tested with a hand-built shader model 5.1 shader and not against RDR2's, which the tree cannot open yet.

## What a bake writes

`or-shader-tool bake-pack` reads the effects of one folder of an install, takes each program a pass of a technique runs, and writes the legalized module of each distinct one to `spirv/<two characters of its key>/<key>.spv`, the key being the SHA-1 of the source container, beside a `manifest.json` (types in `crates/io/or-io/src/gta5/shaders/spirv_pack.rs`). The manifest says, per program, its stage, how it came out (translated, refused or set aside), a fidelity label, the rewrites the legalizer made, how far naga got with it, and its reflection copied unchanged: each binding with its register and the set and binding the layout gives it, the constant buffer layouts, and the input and output signatures. Per effect it says which program each pass of each technique runs at each stage. A module is labelled approximated when a demote became a kill or a clip distance was dropped, and equivalent otherwise. What wrote the modules is the translator build and a hash of the legalizer's sources, and a pack made by another is not reused; a program is reused only if its module is on disk at the size the manifest gives.

At `be06a1db` with this change, on the `win32_40_final` folder of the Legacy install on an Apple M4 Pro, 375 effects bind 4,970 distinct programs, all of which translate: 3,157 are labelled equivalent and 1,813 approximated, and naga writes MSL for 4,751 of them, refuses 107 (75 of them hull, domain and geometry stages) and stops at the parse for 74 and at validation for 38. The modules come to 110 MB. A first run takes 4.9 seconds, and a second run reuses all 4,970 modules and translates none, in 3.8 seconds, nearly all of it reading the archives. The manifest is 16.5 MB: it was 106 MB while each program carried its own constant buffer layouts, which are 20,315 references to 998 distinct layouts and now live in one table keyed by a hash of the layout.

A bake writes the same bytes every time and on every OS. The translator and the legalizer built natively on Linux (aarch64, with the C++ translator compiled by `g++`) say the same identity as on the Mac, and at `ab5912bd` three bakes of the 4,970 programs on the Mac and two on Linux wrote 4,971 files (the modules and the manifest) that match byte for byte. Before that, modules of the 4,970 came out differently from one run to the next (one on the Mac, and on Windows two, each in two variants over eight bakes), because the widening of a location declares a `Private` pointer type ahead of the translator's own of the same type, which it cannot reuse as the translator declares it after the variable, and the clip-distance pass then found both and took whichever a hash map yielded first; it takes the lowest id now (`a_type_declared_twice_is_reused_by_its_first_id_whatever_order_the_maps_iterate_in`, which failed on the old code before it was fixed). `or-shader-tool pack-digest PACK` names a pack by one SHA-1 over its modules and its manifest without the executable's `source_build_hash`, and at `8047e4f6` a Mac bake and the Linux one (with different `--build-hash` values) of the Legacy `win32_40_final` folder both print `4970 modules  06f82cd374114cf86171ff0b38b437cd71b624ef`, which is what a Windows bake of the same install has to print for the MSVC build of the translator to be the same one (`pack-identity` first: the translator `dxbc-spirv c7f06970 bb110db96f2cd195` and the legalizer `a62caa66d826549a`, and an install of another game build will differ in its programs and so in the digest).

An effect also declares a default for most of its constants (12,746 of the 22,153 constants of the Legacy effects, counted at `85ba9cfa`: `globalScalars` is four ones, `globalScalars3` is 16 and a sixteenth, and so on), and the engine binds those before it sets anything. They are not in a program's reflection, and a program is shared by effects that declare different defaults, so the manifest keeps them in the effect, by variable name and as 32-bit words (`Effect::defaults`, which is why the pack's version is 4: an older pack is baked again). A scene fills each buffer in three layers, the effect's defaults, the material's over them and the engine's over those (`a_constant_nothing_sets_holds_what_the_effect_declares_and_a_material_sets_over_it`, `what_the_engine_sets_wins_over_what_the_effect_declares`, `what_the_engine_sets_wins_over_what_a_drawable_carries_for_it`), since a drawable carries a value, left at nought, for what the engine sets on every draw; the four drawables looked at drew nearly as they had, the pistol's lettering a little crisper, so what the defaults fix is the constant nobody sets, and not those.

⚠ The module is the legalized one, the OpenRage profile: valid for Vulkan and for naga, but with clip and cull distances made private, so Vulkan does not yet get the real ones. A raw variant for it is not written. A bake ends by removing the modules no translated program of the new manifest names, which a game update or a translator change leaves behind, and the temporary files a killed run left, and nothing else of the folder (`sweep`); a bake that is killed before it writes the manifest starts over and removes nothing.

## What each platform's writer takes

A module reaches a GPU through a writer of naga's: MSL for Metal, SPIR-V for Vulkan, HLSL for Direct3D 12. `or-shader-tool backend-check PACK` runs the three over every translated program of a baked pack (the Vulkan one twice, with every capability allowed and with only the ones every device has and the few the renderer enables), without a device, so it measures what naga will write and not what a driver then accepts. Of the 4,970 programs of the Legacy `win32_40_final` folder, at `e92de7ae` with this change: **Metal writes 4,751 (95.6%), Vulkan 4,789 (96.4%) by either capability set, and Direct3D 12's HLSL 5.1 4,789 (96.4%)**. The 181 that no writer takes are the 75 hull, domain and geometry programs (naga has no such stage), the 29 compute programs, none of which any writer takes, and 77 vertex and pixel programs the validator or the reader refuses; Metal's writer also panics on 38 more pixel programs that the others write. ## Baked from the app

The editor never loads the translator, which is C++: the app runs `or-shader-tool` as a process and reads the pack it writes. `src/state/game_pack.rs` finds the helper (`OPENRAGE_SHADER_TOOL`, else the file beside the editor), asks it `pack-identity`, which says in one JSON line which translator and legalizer would write a pack now, and starts a bake when the pack under the configuration folder (`shader-pack/game`) is missing or was written by someone else, or from another build of the game: the build is named by the size and age of the executable, which `bake-pack` records as the pack's `source_build_hash`. A bake runs as `bake-pack INSTALL --out ROOT --build-hash HASH --progress`, whose stdout is one `pack_protocol::Event` a line (`reading`, `progress` with the programs done and to do, then `finished`), the type shared by the helper that writes it and the app that reads it, and a log line among them is passed over. It is one job in the job list (`JobKind::GamePackBake`) that can be stopped, which kills the process; a helper that is missing, or was built without its translator, is a status that says so and not a failure to retry; `Automate ▸ Bake game shaders` bakes it again, and a pack named by `OPENRAGE_GAME_PACK` is read and never baked over. Through the real helper, a controller baked the Legacy pack for the folder above, 4,970 programs, in 5.4 seconds on an Apple M4 Pro, and a second controller found it current and started nothing (a run on `91419492` with this change, which the unit tests cannot repeat without an install). The tests stand a script in for the helper, so they run where there is a shell and not on Windows, which this was not run on; and `cargo xtask dist` now builds the helper beside the editor in each package (in `Contents/MacOS` of the app, where the editor looks), as a macOS universal binary joined with `lipo`: the x86_64 and the arm64 builds each compile their C++ in about 40 seconds and say the same translator and legalizer (at `ad11c04c` with this change). A helper that will not build is left out with a warning, since a package without it still opens every asset, and `--require-helper` makes that fatal; the Windows and Linux builds of the C++ were not run.

## Risks

- ⚠ The Enhanced DXIL and RDR2 SPIR-V claims are third-party or unverified until the inventory runs; a wrong one changes which front end a title needs.
- naga's acceptance (typed buffers, format-less UAVs, the early-depth attribute, uniformity) matters on Metal and the DirectX 12 fallback; Vulkan passthrough bypasses it but is unvalidated by wgpu.
- A newer wgpu changes the passthrough descriptor, so the upgrade is decided before anything builds on it.
- dxil-spirv's own tests run on Linux, so macOS and MSVC builds are unproven until the spike.
- Engine constants, pass state and frame order are not in the shader files and need captures and decoding.
